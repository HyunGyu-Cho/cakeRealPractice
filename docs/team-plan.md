> 표기: ✅ 결정됨 · 🟡 제안(검토 필요) · ⬜ 미정
> 이 문서는 합의 기록용이며, 실제 repo 생성·커밋·push 등 git 작업은 팀이 직접 수행한다.

## 2. DB 공유 및 변경 방식

현재 프로젝트는 Flyway 없이 `docs/sql`의 SQL을 수동 적용한다.

| 결정할 사항 | 최종 결정 | 담당자 |
|---|---|---|
| 스키마 공유 방식 | ✅ Flyway 미사용 — `docs/sql` DDL 수동 적용. `docs/sql`도 repo에 포함해 코드와 함께 버전관리 | |
| SQL 파일명과 실행 순서 규칙 | 🟡 `V0/V1…` 번호 규칙 사용(현재 `V0_ERD`·`V1_first_MVC_table`). 스키마 오너·변경 내용은 PR 설명에 명시 | |
| SQL 검토자 | ⬜ | |
| 공용 RDS 반영 담당자 | ⬜ | |
| RDS 적용 이력 기록 위치 | ⬜ | |
| 적용 실패 시 롤백 방법 | ⬜ | |
| 테이블·컬럼·제약조건 네이밍 규칙 | ✅ [`conventions.md`](conventions.md) 데이터베이스 규약 준수 | |
| 로컬 seed와 공용 seed의 구분 기준 | ⬜ `V1_first_MVC_table.sql`이 테이블(rds 필요)과 샘플 계정·매장 시드(local 전용)를 함께 담고 있어 분리 여부 결정 필요 | |

### 원칙

- DB 구조의 정본은 `docs/sql`로 한다.
- 공용 RDS에 적용한 SQL 파일은 수정하지 않고 새 변경 파일을 추가한다.
- SQL은 로컬 DB에서 검증하고 PR 검토를 거친 후 RDS에 반영한다.
- 대량 테스트 데이터는 공용 RDS에 넣지 않는다.

## 6. 업무 분담과 도메인 간 인터페이스

### 담당 영역

도메인 = `feature/*` 브랜치 단위로 작업해 충돌을 최소화한다.

| 팀원 | 담당 도메인 |
|---|---|
| 수민 | `member`, `cart` |
| 주환 | `order`, `payment` |
| 정후 | `coupon` |
| 민정 | `chat`, `notification` |
| 현규 | `community`, `review` |
| 시은 | `product` |
| 공통 | `store`, `global/*`, `home` (7번 오너십 규약대로 PR 합의 후 변경) |
| 후반 별도 | `statistics` |

- `home`: 전용 Mapper 없이 각 도메인 공개 View를 단방향 조합하는 얇은 계층 — 이미 매장 조회에 연결됨. 별도 개발 대상 아님. 각 도메인이 완성되면 자기 공개 View를 home에 물려주기만 하면 된다.
- `statistics`: 타 도메인 데이터에 의존·목업 상태 → 각 도메인 완성 후 후반에 별도로 착수(담당 추후 결정).

> ⚠️ **결제 흐름 3인 공유**: `cart`(수민) → `order`·`payment`(주환) ← `coupon`(정후)이 `OrderStatus` 상태 전이와 checkout 흐름을 공유한다. 착수 초반에 셋이 인터페이스(장바구니→주문 생성 · 쿠폰 적용 시점 · 결제 상태 콜백)를 먼저 맞추고 각자 브랜치를 판다. 충돌·재작업이 가장 많이 나는 지점이다.

### 도메인 간 연결

| 연결 | 합의할 기능과 데이터 | 담당자 |
|---|---|---|
| 장바구니 → 상품 | 상품·옵션·현재 가격 확인 | |
| 주문 → 회원·장바구니·상품 | 주문자, 주문 대상, 재고 확인 | |
| 결제 → 주문 | 결제 가능 여부와 주문 상태 변경 | |
| 쿠폰 → 주문 | 할인 계산, 사용 및 복구 | |
| 리뷰 → 주문 | 구매·픽업 완료 확인 | |
| 알림 → 주문·결제 | 이벤트별 알림 생성 | |
| 채팅 → 회원·주문 | 상담 대상과 주문 정보 조회 | |

### 원칙

- FK 또는 공통 인터페이스 변경은 관련 담당자 모두가 검토한다.
- 다른 도메인은 Mapper가 아니라 합의된 Service 인터페이스를 통해 사용한다.
- 여러 도메인이 참여하는 작업은 트랜잭션을 소유할 도메인을 먼저 정한다.

## 8. 핵심 비즈니스 규칙

> 일부 항목은 고객 목업 JS(`static/js/customer-mockup.js`)가 브라우저 안에서 임시 동작을 시연하고 있다.
> 이는 기획 의도를 보여주는 **임시 답(🟡)**일 뿐 확정 규칙이 아니다. 담당자가 백엔드 착수 시
> 해당 화면의 목업 JS 동작을 읽고 규칙을 확정한 뒤(이 표 갱신), service에 구현한다.

| 결정할 사항 | 최종 결정 | 관련 담당자 |
|---|---|---|
| 같은 상품·옵션을 장바구니에 다시 담을 때 처리 | 🟡 목업 JS 임시 동작: 같은 상품+같은 픽업 일시면 수량 합산(재고 상한), 픽업 일시가 다르면 별도 항목 | |
| 장바구니 가격과 현재 가격이 다를 때 처리 | 🟡 목업 JS 임시 동작: 담은 시점 가격을 그대로 사용(재조회 없음) — 서버 구현 시 신뢰 불가, 재검증 방식 확정 필요 | |
| 주문 시 상품명·옵션명·가격 스냅샷 저장 여부 | 🟡 DDL은 스냅샷 방식 반영됨: `order_items`에 `product_name`·`product_type`·`base_price`·`option_amount` 컬럼 보유. 목업 JS도 동일 방식 | |
| 재고 차감 및 복구 시점 | | |
| 관리자 승인 전후 주문 수정·취소 가능 여부 | 🟡 취소 전이 자체는 `OrderStatus.canTransitionTo()` 확정(최종 전 모든 상태 → CANCELED). 수정 가능 범위·취소 주체·시한은 미정 | |
| 결제 성공과 주문 상태 변경 순서 | | |
| 결제 성공 후 DB 처리 실패 시 복구 방법 | | |
| 전체 취소와 부분 취소 지원 범위 | | |
| 쿠폰 사용 및 복구 시점 | | |
| 리뷰 작성 가능 조건과 작성 가능 횟수 | | |

## 10. `application.yml` 로컬값 처리

⚠️ `application.yml`은 gitignore에 없어 추적된다. 각자의 로컬 DB 접속값을 커밋하면 서로 덮어쓴다.

| 해결안(택1) | 내용 |
|---|---|
| (a) | `application.yml`엔 공통값만, 개인 로컬값은 `application-local.yml`(gitignore)로 분리 |
| (b) | 로컬 datasource도 `.env` 방식으로 통일 |

> 현재는 `local` 프로필의 로컬 DB 값도 `.env`(`LOCAL_DB_*`)에서 읽도록 되어 있어 (b)에 가깝다. 최종 채택안을 확정한다.
