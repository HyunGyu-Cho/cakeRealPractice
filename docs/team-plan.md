> 표기: ✅ 결정됨 · 🟡 제안(검토 필요) · ⬜ 미정
> 이 문서는 합의 기록용이며, 실제 repo 생성·커밋·push 등 git 작업은 팀이 직접 수행한다.

## 2. DB 공유 및 변경 방식

현재 프로젝트는 Flyway로 스키마를 관리한다(2026-07-27 전환, 배경은 [`flyway-migration-proposal.md`](flyway-migration-proposal.md)). 전환 이전 이력은 `docs/sql/legacy`에 보관한다.

| 결정할 사항 | 최종 결정 | 담당자 |
|---|---|---|
| 스키마 공유 방식 | ✅ Flyway — `src/main/resources/db/migration`을 앱 부팅 시 자동 적용. 코드와 함께 버전관리되며 수동 적용은 하지 않는다 | |
| SQL 파일명과 실행 순서 규칙 | ✅ Flyway 규칙 `V<번호>__<설명>.sql`(언더바 2개). 개발용 시드는 `db/seed/R__dev_seed.sql`. 스키마 오너·변경 내용은 PR 설명에 명시 | |
| SQL 검토자 | ⬜ | |
| 공용 RDS 반영 담당자 | ⬜ | |
| RDS 적용 이력 기록 위치 | ✅ RDS의 `flyway_schema_history` 테이블(적용 시각·체크섬·성공 여부 자동 기록) | |
| 적용 실패 시 롤백 방법 | 🟡 Flyway Community는 자동 undo가 없다. 되돌리는 변경을 새 V파일로 추가하는 것이 기본. 파괴적 변경은 적용 전 RDS 스냅샷 | |
| 테이블·컬럼·제약조건 네이밍 규칙 | ✅ [`conventions.md`](conventions.md) 데이터베이스 규약 준수 | |
| 로컬 seed와 공용 seed의 구분 기준 | ✅ 기준은 "없으면 앱이 동작하지 않는가" 하나다. **필수 시드**(categories·대표 매장 1행+7요일·post_categories)는 `db/migration`, **데모 시드**(샘플 계정·상품/주문제작 샘플)는 `db/seed`에 둔다. `db/seed`는 `local` 프로필에서만 `flyway.locations`에 들어가므로 구분이 문서가 아니라 **설정으로 강제된다** — 표는 [README DB 스키마 관리 > 시드 구분](../README.md#시드-구분-로컬-vs-공용-rds) | 공용 RDS는 샘플 관리자 계정을 쓰지 않고 별도 계정을 만든다(해시가 저장소에 공개돼 있어 `db/seed`로 내렸다) |

### 원칙

- DB 구조의 정본은 `src/main/resources/db/migration`으로 한다.
- 커밋된 마이그레이션 파일은 수정하지 않고 새 변경 파일을 추가한다(Flyway 체크섬 검증).
- SQL은 로컬 DB에서 검증하고 PR 검토를 거친 후 RDS에 반영한다.
- 대량 테스트 데이터는 공용 RDS에 넣지 않는다.

## 3. 테스트 계정

공통 계정, 개인 계정, 워크플로우 계정을 구분한다.

| 구분 | 용도 | 계정 또는 규칙 | 관리 담당자 |

| 공통 관리자 | 관리자 기능 확인 | 🟡 `admin` (day1) | |

| 개인 계정 | 개인 기능 개발 | ⬜ | |
| 주문 계정 | 주문 생성·승인·취소 흐름 | 🟡 `buyer`(PICKED_UP) · `custom`(UNDER_REVIEW) | |

- 공통 계정의 기본 정보와 초기 상태를 임의로 변경하지 않는다.

- 공통계정 비밀번호는 Git이 아닌 합의된 장소에서 공유한다.

| Form DTO·View DTO·Entity의 사용 기준 | ✅ [`conventions.md`](conventions.md) 준수 | |
| 도메인 간 DTO·Entity 직접 공유 허용 여부 | ⬜ (원칙: 합의된 Service 인터페이스로만 연동) | |

### 원칙

- Controller에서 Mapper를 직접 호출하지 않는다.

- 입력 검증은 Form DTO, 비즈니스 검증은 Service에서 처리한다.
- 프론트 템플릿 규격은 [`frontend-template-format.md`](frontend-template-format.md) 기준(공통 프래그먼트·`app.css`·`app.js` 재사용).

## 6. 업무 분담과 도메인 간 인터페이스

### 담당 영역

도메인 = `feature/*` 브랜치 단위로 작업해 충돌을 최소화한다.

| 팀원 | 담당 도메인 |
|---|---|
| 수민 | `member`, `cart` |
| 주환 | `order`, `payment` |
| 정후 | `coupon` |
| 민정 | `chat`, `notification` |
| 현규 | `community`, `review` |
| 시은 | `product` |
| 공통 | `store`, `global/*`, `home` (7번 오너십 규약대로 PR 합의 후 변경) |
| 후반 별도 | `statistics` |

- `home`: 전용 Mapper 없이 각 도메인 공개 View를 단방향 조합하는 얇은 계층 — 이미 매장 조회에 연결됨. 별도 개발 대상 아님. 각 도메인이 완성되면 자기 공개 View를 home에 물려주기만 하면 된다.
- `statistics`: 타 도메인 데이터에 의존 → 전 도메인 완성 후 후반에 별도로 착수. 구현 완료(현규, 스펙 `docs/specs/statistics.md`).
  `home`과 같은 얇은 조합 계층이라 자기 테이블·Mapper가 없고 집계 SQL은 각 도메인이 소유한다.

> ⚠️ **결제 흐름 3인 공유**: `cart`(수민) → `order`·`payment`(주환) ← `coupon`(정후)이 `OrderStatus` 상태 전이와 checkout 흐름을 공유한다. 착수 초반에 셋이 인터페이스(장바구니→주문 생성 · 쿠폰 적용 시점 · 결제 상태 콜백)를 먼저 맞추고 각자 브랜치를 판다. 충돌·재작업이 가장 많이 나는 지점이다.

### 도메인 간 연결

| 연결 | 합의할 기능과 데이터 | 담당자 |
|---|---|---|
| 장바구니 → 상품 | 상품·옵션·현재 가격 확인 | |
| 주문 → 회원·장바구니·상품 | 주문자, 주문 대상, 재고 확인 | |
| 결제 → 주문 | 결제 가능 여부와 주문 상태 변경 | |
| 쿠폰 → 주문 | 할인 계산, 사용 및 복구 | |
| 리뷰 → 주문 | 구매·픽업 완료 확인 | |
| 알림 → 주문·결제 | 이벤트별 알림 생성 | |
| 채팅 → 회원·주문 | 상담 대상과 주문 정보 조회 | |

### 원칙

- FK 또는 공통 인터페이스 변경은 관련 담당자 모두가 검토한다.
- 다른 도메인은 Mapper가 아니라 합의된 Service 인터페이스를 통해 사용한다.
- 여러 도메인이 참여하는 작업은 트랜잭션을 소유할 도메인을 먼저 정한다.

## 8. 핵심 비즈니스 규칙

> **전 항목 확정 완료.** 초기에는 고객 목업 JS(`static/js/customer-mockup.js`)가 브라우저 안에서
> 시연하던 임시 동작(🟡)이 답을 대신하고 있었으나, 각 도메인이 실구현되면서 모두 service가 소유하는
> 확정 규칙(✅)으로 대체됐다. 규칙을 바꿀 때는 이 표와 해당 도메인 스펙(`docs/specs/`)을 함께 고친다.

| 결정할 사항 | 최종 결정 | 관련 담당자 |
|---|---|---|
| 같은 상품·옵션을 장바구니에 다시 담을 때 처리 | ✅ 동일 회원·동일 상품은 한 항목으로 합산한다(`(cart_id, product_id)` UNIQUE). 수량 상한은 현재 재고이고 별도 10개 제한은 없다. 목업의 "픽업 일시가 다르면 별도 항목"은 성립하지 않는다 — 픽업 일시는 주문 단계 값이라 장바구니에 저장하지 않는다. `CUSTOM`은 담을 수 없다 | 수민 |
| 장바구니 가격과 현재 가격이 다를 때 처리 | ✅ 담은 가격을 **아예 저장하지 않는다**. `cart_items`는 상품·수량만 갖고, 조회·수량 변경·주문 인계마다 `ProductService.getSalesInfo()`로 최신 가격·판매 여부·재고를 재검증한다. 판매 중지·품절 항목은 자동 삭제하지 않고 비활성으로 표시해 선택·주문만 막는다 | 수민 |
| 주문 시 상품명·옵션명·가격 스냅샷 저장 여부 | ✅ 저장한다. 결제 성공 트랜잭션에서 `order_items`에 `product_name`·`product_type`·`base_price`·`option_amount`와 `preparation_days`·`cancellation_limit_days`까지 함께 스냅샷하므로, 이후 상품이 바뀌거나 삭제돼도 주문 내역은 주문 시점 값을 보여준다 | 주환 |
| 재고 차감 및 복구 시점 | ✅ 결제 성공 트랜잭션에서 조건부 차감, 전액 취소 트랜잭션에서 정확히 복구 | |
| 관리자 승인 전후 주문 수정·취소 가능 여부 | ✅ 요청서 수정은 지원하지 않는다(반려·취소 후 새 요청서 작성). 고객 취소는 견적 수락 전까지, 관리자 취소는 `IN_PRODUCTION`까지. 결제 후에는 일반 주문 취소 규칙(`pickup_at - cancellation_limit_days`)을 따른다 | 주환 |
| 주문제작 요청·견적 처리 방식 | ✅ 요청서는 전용 테이블 없이 `orders`(`UNDER_REVIEW`) + `order_items` 계열로 저장하고 초안은 저장하지 않는다. 견적 진행은 `orders.status`가 아니라 `custom_order_quotes`가 소유하며 재견적은 회차(`version`) 행을 누적하고 이전 행을 `SUPERSEDED`로 내린다. 최종 금액은 관리자 견적이고 고객 수락 시 `orders.final_amount`를 확정한다 | 주환 |
| 결제 링크 만료 정책 | ✅ 견적당 링크 1건(UNIQUE), 일회성 토큰, 유효기간은 발급 후 72시간과 견적 제작 가능일 전날 중 이른 쪽. 재견적·주문 취소 시 `REVOKED`. 중복 결제는 링크 UNIQUE + `FOR UPDATE` 재확인 + `payments.idempotency_key` UNIQUE로 3중 방어 | 주환 |
| 픽업 예약 창과 슬롯 정원 | ✅ 예약 창은 유형별 — 일반 14일(결제 시 재고가 묶이므로), 주문제작 90일(재고 미관리·긴 리드타임). **한 슬롯에 주문 1건**만 받고 예약된 시각은 목록에서 빠진다(취소·반려분은 다시 열림). 픽업 예정 주문이 있는 날짜는 휴무일로 지정할 수 없고 건수를 함께 안내한다. 예약 현황은 store가 정의한 `PickupReservationPort`를 order가 구현해 넘긴다(store가 orders를 직접 읽으면 순환) | 주환·공통 |
| 결제 성공과 주문 상태 변경 순서 | ✅ 외부 승인 없는 모의 결제에서 주문 `PAID`와 결제 `DONE`을 같은 트랜잭션에 생성 | |
| 결제 성공 후 DB 처리 실패 시 복구 방법 | ✅ 재고·주문·결제·장바구니 삭제 전체 롤백, 초안과 장바구니 유지 | |
| 전체 취소와 부분 취소 지원 범위 | ✅ 일반 주문은 전액 취소만 지원, 부분 취소는 후속 범위 | |
| 쿠폰 사용 및 복구 시점 | ✅ 사용은 결제 트랜잭션 안에서 `AVAILABLE → USED` 조건부 UPDATE, 복구는 주문 취소 트랜잭션 안에서 `USED → AVAILABLE`. 체크아웃 초안 단계에서는 잡아두지 않는다 | 정후 |
| 리뷰 작성 가능 조건과 작성 가능 횟수 | ✅ 본인 주문이 `PICKED_UP`인 **주문 항목당 1개**(`uk_reviews_order_item`). 같은 상품을 여러 번 사면 각각 쓴다. 삭제하면 그 항목에 다시 쓸 수 있다 | 현규 |
| 채팅방 생성·종료 시점 | ✅ 고객의 첫 메시지에 고객별 영구 방 1개 생성. 관리자가 `CLOSED`로 종료하며 고객이 메시지 또는 `/주문제작`을 보내면 `OPEN`으로 자동 재개 | 민정 |
| 통계 매출·집계 기준 | ✅ 매출의 정본은 payment다 — 순매출 = 승인 결제(`payments.approved_at`) − 완료된 취소(`payment_cancellations.canceled_at`). order는 `orders.final_amount` 기준 "주문 금액"까지만 노출하고 결제 테이블을 JOIN하지 않는다. 주문 건수는 `created_at`, 완료·취소는 기간 내 `picked_up_at`·`canceled_at` 발생 기준이며 상품별 집계는 취소·반려를 제외한다. 재고 부족 임계는 5개, 신규 회원은 탈퇴자 포함, 평균 평점은 `VISIBLE` 후기만. statistics는 자기 테이블·Mapper 없이 각 도메인 공개 Service만 조합한다 | 현규 |
| 알림 생성 범위와 읽음 처리 방식 | ✅ 생성 범위는 채팅(발신자 반대편)·결제 완료·주문 상태 전이·취소환불·후기 답글 등록 13개 `NotificationType`(후기 답글은 V19에서 추가). 고객은 본인, 관리자는 전체 ADMIN 팬아웃. 업무 트랜잭션과 같은 트랜잭션에 저장(트랜잭션에 남는 것은 INSERT뿐 — 회원 조회·푸시는 커밋 후)하고 실시간 푸시는 커밋 후 개인 큐로 보낸다(고객·관리자 공통, 공용 토픽 없음). 푸시 실패는 롤백하지 않고 `notification_deliveries`에 남겨 스케줄러가 최대 3회 재시도한다. 읽음은 `is_read` 불리언 단방향·멱등이며 수신자 본인만 처리 | 민정 |

- `main`에는 직접 push하지 않고 PR로 병합한다.

## 10. `application.yml` 로컬값 처리

⚠️ `application.yml`은 gitignore에 없어 추적된다. 각자의 로컬 DB 접속값을 커밋하면 서로 덮어쓴다.

| 해결안(택1) | 내용 |
|---|---|
| (a) | `application.yml`엔 공통값만, 개인 로컬값은 `application-local.yml`(gitignore)로 분리 |
| (b) | 로컬 datasource도 `.env` 방식으로 통일 |

> ✅ `local` 프로필도 `.env`의 `LOCAL_DB_*`를 읽는 방식으로 확정했다. 프로필 누락 시 공용 RDS에 접속하지 않도록 `local`을 기본 프로필로 사용한다.
