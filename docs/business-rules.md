# 확정 업무 규칙

## 이 문서는 무엇인가

"장바구니에 같은 케이크를 또 담으면 줄이 두 개 생기나, 수량만 늘어나나?"
"주문한 뒤에 가게가 가격을 올리면 내 주문서 금액도 오르나?"

이런 질문에 **답이 하나로 정해져 있어야** 프로그램이 일관되게 동작한다.
말로만 정하면 사람마다 다르게 기억하므로, 정한 답을 여기 적어 둔다.

- **코드 작성 방법**이 아니라 **"무엇이 옳은가"** 를 담는다. 코드 규약은 [`conventions.md`](conventions.md).
- 여기 규칙은 전부 **이미 코드로 구현돼 있다.** 앞으로 정할 것이 아니라 이미 정해진 것이다.
- 각 규칙은 해당 도메인의 **Service가 소유**한다(Service가 무엇인지는 [용어 사전](conventions.md#용어-사전)).

> ⚠️ **규칙을 바꿀 때는 이 문서와 `docs/specs/<도메인>.md`를 함께 고친다.**
> 한쪽만 고치면 두 문서가 서로 다른 말을 하게 되고, 나중에 누가 옳은지 알 수 없다.

**모르는 용어가 나오면** [`conventions.md` 용어 사전](conventions.md#용어-사전)을 본다
(트랜잭션·멱등·스냅샷·파생값 등).

## 1. 장바구니

| 규칙 | 내용 |
|---|---|
| 같은 상품·옵션을 다시 담을 때 | 동일 회원·동일 상품은 **한 항목으로 합산**한다(`(cart_id, product_id)` UNIQUE). 수량 상한은 현재 재고이고 별도 10개 제한은 없다. 픽업 일시는 주문 단계 값이라 장바구니에 저장하지 않으므로 "일시가 다르면 별도 항목"은 성립하지 않는다. `CUSTOM` 상품은 담을 수 없다 |
| 담은 가격과 현재 가격이 다를 때 | 담은 가격을 **아예 저장하지 않는다.** `cart_items`는 상품·수량만 갖고, 조회·수량 변경·주문 인계마다 `ProductService.getSalesInfo()`로 최신 가격·판매 여부·재고를 재검증한다. 판매 중지·품절 항목은 자동 삭제하지 않고 비활성으로 표시해 선택·주문만 막는다 |

## 2. 주문

| 규칙 | 내용 |
|---|---|
| 주문 시 스냅샷 저장 | 저장한다. 결제 성공 트랜잭션에서 `order_items`에 `product_name`·`product_type`·`base_price`·`option_amount`와 `preparation_days`·`cancellation_limit_days`까지 함께 스냅샷한다. 이후 상품이 바뀌거나 삭제돼도 주문 내역은 주문 시점 값을 보여준다 |
| 재고 차감·복구 시점 | 결제 성공 트랜잭션에서 조건부 차감, 전액 취소 트랜잭션에서 정확히 복구 |
| 취소 가능 범위 | 고객 취소는 견적 수락 전까지, 관리자 취소는 `IN_PRODUCTION`까지. 결제 후에는 일반 주문 취소 규칙(`pickup_at - cancellation_limit_days`)을 따른다 |
| 전체/부분 취소 | 일반 주문은 **전액 취소만** 지원한다. 부분 취소는 후속 범위 |
| 픽업 예약 창과 슬롯 | 예약 창은 유형별 — 일반 14일(결제 시 재고가 묶이므로), 주문제작 90일(재고 미관리·긴 리드타임). **한 슬롯에 주문 1건**만 받고 예약된 시각은 목록에서 빠진다(취소·반려분은 다시 열림). 픽업 예정 주문이 있는 날짜는 휴무일로 지정할 수 없고 건수를 함께 안내한다. 예약 현황은 store가 정의한 `PickupReservationPort`를 order가 구현해 넘긴다(store가 orders를 직접 읽으면 순환) |

## 3. 주문제작

| 규칙 | 내용 |
|---|---|
| 요청서 저장 방식 | 전용 테이블 없이 `orders`(`UNDER_REVIEW`) + `order_items` 계열로 저장하고 초안은 저장하지 않는다 |
| 요청서 수정 | **지원하지 않는다.** 반려·취소 후 새 요청서를 작성한다 |
| 견적 진행 | `orders.status`가 아니라 `custom_order_quotes`가 소유한다. 재견적은 회차(`version`) 행을 누적하고 이전 행을 `SUPERSEDED`로 내린다. 최종 금액은 관리자 견적이고 고객 수락 시 `orders.final_amount`를 확정한다 |
| 결제 링크 | 견적당 링크 1건(UNIQUE), 일회성 토큰, 유효기간은 발급 후 72시간과 견적 제작 가능일 전날 중 **이른 쪽**. 재견적·주문 취소 시 `REVOKED`. 중복 결제는 링크 UNIQUE + `FOR UPDATE` 재확인 + `payments.idempotency_key` UNIQUE로 3중 방어 |

## 4. 결제

| 규칙 | 내용 |
|---|---|
| 제공자 선택 | `cakeshop.payment.provider` 설정으로 고른다(`mock` 기본 / `toss`). 도메인 로직은 하나이고 `PaymentGateway` 구현만 갈린다 |
| 결제와 주문 상태 순서 | 승인 성공 후 확정 트랜잭션에서 주문 `PAID`와 결제 `DONE`을 함께 만든다. **외부 호출은 DB 트랜잭션 밖**이다 |
| 확정 실패 시 복구 | 재고·주문·결제·장바구니 삭제 전체 롤백, 초안과 장바구니 유지. 승인은 됐는데 확정이 실패하면 즉시 취소를 호출하고 `ABORTED`로 마감한다 — 돈만 빠져나간 상태를 만들지 않는다 |
| 웹훅 | 저장만 하고 즉시 200(10초 제한). 전송 ID UNIQUE가 재전송을 막고 반영은 `WebhookEventProcessor`가 따로 한다 |

## 5. 쿠폰

| 규칙 | 내용 |
|---|---|
| 사용·복구 시점 | 사용은 결제 트랜잭션 안에서 `AVAILABLE → USED` 조건부 UPDATE, 복구는 주문 취소 트랜잭션 안에서 `USED → AVAILABLE`. **체크아웃 초안 단계에서는 잡아두지 않는다** |

## 6. 후기

| 규칙 | 내용 |
|---|---|
| 작성 조건과 횟수 | 본인 주문이 `PICKED_UP`인 **주문 항목당 1개**(`uk_reviews_order_item`). 같은 상품을 여러 번 사면 각각 쓴다. 삭제하면 그 항목에 다시 쓸 수 있다 |

## 7. 채팅

| 규칙 | 내용 |
|---|---|
| 방 생성·종료 | 고객의 첫 메시지에 **고객별 영구 방 1개** 생성. 관리자가 `CLOSED`로 종료하며, 고객이 메시지 또는 `/주문제작`을 보내면 `OPEN`으로 자동 재개 |

## 8. 알림

| 규칙 | 내용 |
|---|---|
| 생성 범위 | 채팅(발신자 반대편)·결제 완료·주문 상태 전이·취소환불·후기 답글 등록 — `NotificationType` 13개 |
| 수신자 | 고객은 본인, 관리자는 전체 ADMIN 팬아웃 |
| 저장과 푸시 | 업무 트랜잭션과 **같은 트랜잭션에 저장**한다(트랜잭션에 남는 것은 INSERT뿐 — 회원 조회·푸시는 커밋 후). 실시간 푸시는 커밋 후 개인 큐로 보낸다(고객·관리자 공통, 공용 토픽 없음) |
| 푸시 실패 | 롤백하지 않고 `notification_deliveries`에 남겨 스케줄러가 최대 3회 재시도 |
| 읽음 처리 | `is_read` 불리언 단방향·멱등이며 수신자 본인만 처리 |
| 후기 답글 알림 | **최초 등록에만 발행하고 수정은 재발행하지 않는다.** 답글은 후기당 1개라 수정마다 보내면 같은 답글로 작성자를 반복해 깨우게 된다 |

## 9. 통계

| 규칙 | 내용 |
|---|---|
| 매출의 정본 | **payment다.** 순매출 = 승인 결제(`payments.approved_at`) − 완료된 취소(`payment_cancellations.canceled_at`). order는 `orders.final_amount` 기준 "주문 금액"까지만 노출하고 결제 테이블을 JOIN하지 않는다 |
| 집계 기준 | 주문 건수는 `created_at`, 완료·취소는 기간 내 `picked_up_at`·`canceled_at` 발생 기준. 상품별 집계는 취소·반려를 제외한다 |
| 임계값 | 재고 부족 5개, 신규 회원은 탈퇴자 포함, 평균 평점은 `VISIBLE` 후기만 |
| 소유 범위 | statistics는 자기 테이블·Mapper 없이 각 도메인 공개 Service만 조합한다 |

## 도메인 간 연동

다른 도메인의 테이블을 직접 JOIN하지 않고, 상대가 공개한 **Service 인터페이스**로만 연동한다.

| 연결 | 주고받는 것 |
|---|---|
| 장바구니 → 상품 | 상품·옵션·현재 가격 확인 (`ProductService.getSalesInfo()`) |
| 주문 → 회원·장바구니·상품 | 주문자, 주문 대상, 재고 확인 |
| 결제 → 주문 | 결제 가능 여부와 주문 상태 변경 |
| 쿠폰 → 주문 | 할인 계산, 사용 및 복구 |
| 후기 → 주문 | 구매·픽업 완료 확인 |
| 알림 → 주문·결제 | 이벤트별 알림 생성 |
| 채팅 → 회원·주문 | 상담 대상과 주문 정보 조회 |
| 매장 ← 주문 | 픽업 예약 현황 (`PickupReservationPort` — store가 정의하고 order가 구현) |

- FK나 공개 인터페이스를 바꿀 때는 관련 도메인을 함께 검토한다.
- 여러 도메인이 참여하는 작업은 **트랜잭션을 소유할 도메인을 먼저 정한다.**

> ⚠️ **결제 흐름은 3개 도메인이 공유한다.** `cart` → `order`·`payment` ← `coupon`이
> `OrderStatus` 전이와 checkout 흐름을 공유하므로, 인터페이스를 바꾸기 전에 셋을 함께 본다.

## 파일·이미지 저장

| 항목 | 규칙 |
|---|---|
| 저장 위치 | 프로젝트 **밖** 로컬 디렉토리(`.env`의 `FILE_UPLOAD_DIR`, 기본 `<user home>/cakeshop-uploads`) |
| 저장·서빙 | `LocalFileStorageClient`가 저장하고 `/uploads/**`로 서빙한다 |
| DB에 저장할 값 | 웹 접근 경로(`url-prefix` 접두) |
| 확장자 결정 | **파일명이 아니라 content type에서 역산**한다 — 공개 서빙 경로에 실행 가능한 파일이 생기지 않게 |
| 검증 | `global/infra/ImageValidator` — 형식 화이트리스트 + 크기 + 실제 파일 머리 바이트 |
| 롤백 시 정리 | 파일 시스템은 트랜잭션에 참여하지 않는다. `@Transactional` 안에서 파일을 쓰면 `StoredFileCleanup`에 반드시 등록한다 |
| 채팅 이미지 | `/uploads/**` 공개 경로와 분리하고 소유권 검사 API로만 읽는다(`CHAT_IMAGE_DIR`) |

## 기능 완료 기준

- 정상 흐름과 주요 실패 흐름이 동작한다.
- 입력 검증과 접근 권한이 적용된다.
- 상태 전이와 트랜잭션 규칙을 지킨다.
- 관련 자동화 테스트가 통과한다 — 실구현 도메인은 **Service 업무 규칙 + Controller 검증/PRG** 전용 테스트를 둔다. Mapper XML은 머지 검증의 로컬 DB 부팅·화면 스모크로 실행을 확인한다.
- 필요한 마이그레이션과 문서를 함께 수정한다.
