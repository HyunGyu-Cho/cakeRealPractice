1. 완성도 평가 — dev 기준

main 기준 평가(2/13 도메인, 25%)와는 전혀 다른 그림이다. 13개 도메인 전부 실구현이고 목업 화면이 남아 있지 않다. main 소스 316개 파일 / 약 16,500줄, 테스트 84개 클래스(main 브랜치의 10배). Flyway 도입 완료(V1~V3 + R__dev_seed), GitHub Actions CI(빌드·스키마 재현·테스트, MariaDB 서비스 컨테이너), 도메인별 스펙 문서(docs/specs/)와 스펙 미승인 시 코드 수정을 차단하는 훅까지 — 협업 가드레일 수준은 팀 프로젝트 기준 상위 1% 수준이다.

도메인 집계 조합 — 날짜 인덱스 없이 풀스캔 (개선점 ⑤)

잘 되어 있는 점 (main 평가에서 상향)

  • 스키마 관리 체계 — Flyway V파일 불변 규칙 + CI에서 빈 DB에 스키마 재현 검증. main에서 지적했던 "수동 DDL, README 순서 오류" 문제가 구조적으로 해소됐다.
  • 도메인별 인덱스 설계 — orders(member+created, status+pickup), payments, reviews, coupons, notifications 모두 조회 패턴에 맞는 복합 인덱스를 보유. 인덱스를 "아는" 팀이다.
  • 협업 규율 — 브랜치 보호 + 필수 CI 체크, 스펙 승인 훅, 도메인 간 직접 JOIN 금지 규칙이 문서가 아니라 도구로 강제된다.

남은 공백 (이번 측정으로 확인)

  • posts·comments만 보조 인덱스가 없다 — 다른 도메인과 대비되는 유일한 공백. 메인 페이지가 매 요청 posts 풀스캔(11초)을 타는 것이 최대 리스크였다.
  • 좋아요 토글 데드락 — 부하에서 실제 재현(2회 실행 모두). check-then-act + 갭락 교차가 원인.
  • LIKE '%…%' 검색(게시글 제목·주문번호), 통계 대시보드의 날짜 컬럼 풀스캔, 조회수 핫로우는 여전히 남아 있다.

종합: dev는 기능 완성 단계(약 90%)에 들어선 코드베이스다. 이제 병목은 "기능이 없는 것"이 아니라 "데이터가 쌓였을 때의 성능"이며, 그 1순위가 커뮤니티였다.

2. 모니터링 방법 — CS 지식과 함께

구성은 이전 리포트와 동일한 3계층 관측(앱: Actuator/Prometheus 관리 포트 분리 · DB: slow log/EXPLAIN/GLOBAL STATUS · 대시보드: Grafana)이다. dev에서는 measurement 대상을 넓혀 10가지 실제 사용자 행동을 재현했다: 메인 인기 글(모든 방문자), 커뮤니티 목록·무한스크롤·상세·좋아요, 관리자 게시글 검색, 마이페이지 주문 조회, 관리자 주문 목록, 주문번호 검색, 통계 대시보드.

  • p50/p95로 롱테일 확인 — 평균은 병목을 숨긴다. 기준 부하에서 무한스크롤 p50 7.3초 vs p95 13.9초.
  • Handler_read_rnd_next 495만/15초 — 인덱스 없이 순차 스캔한 행 수. 풀스캔의 직접 증거.
  • 데드락 검출 — InnoDB는 잠금 대기 그래프에서 사이클을 찾으면 한쪽 트랜잭션을 강제 롤백한다(에러 1213). 부하 테스트가 아니면 코드 리뷰로 잡기 어려운 유형.
  • 이 샌드박스는 Maven Central이 차단되어 앱 부팅이 불가하므로 DB 계층에서 실측했다. 앱 계층 지표는 로컬에서 --spring.profiles.active=local,monitor 실행 후 localhost:9090/actuator/prometheus로 확인.

부하 중 검출된 데드락 — 좋아요 토글

(1213) Deadlock found when trying to get lock; try restarting transaction  ← 2회 실행 모두 발생

원인(CS): 토글 = SELECT EXISTS → INSERT/DELETE(post_likes) → UPDATE(posts.like_count)
  T1: post_likes UNIQUE 인덱스에 INSERT 의향 잠금(갭락) 획득 → posts 행 잠금 대기
  T2: 같은 인기글에서 DELETE로 post_likes 행·갭 잠금 → posts 행 잠금 획득 → T1의 갭과 충돌
  → 대기 그래프에 사이클 → InnoDB가 한쪽을 강제 롤백 (사용자에게는 500 에러)

동시성이 높은 인기글에서 반복될 유형이다. 해결은 개선점 ④.

4. 개선점과 해결 방법

적용 완료① V4 커뮤니티 인덱스 4개 — db/migration/V4__community_performance_indexes.sql

posts(status,id) · posts(category_id,status,id) · posts(status,like_count,id — 인기 글 전용) · comments(post_id,status). 팀 규칙대로 기존 V파일을 수정하지 않고 새 V4로 추가했다. Flyway가 각 팀원 로컬 DB와 CI에 자동 적용한다. 실측: 인기 글 11,069ms → 2.8ms (인덱스 역방향 스캔), 통계용 카운트 2,233ms → 49ms.

적용 완료② 목록·인기글 쿼리 리라이트 (late row lookup) — CommunityMapper.xml

파생테이블에서 id만 인덱스로 LIMIT 건수까지 좁힌 뒤 확정된 소수 행에만 JOIN·댓글수 서브쿼리를 실행. 인덱스만으로는 부족했던 이유: 옵티마이저가 4행짜리 카테고리 조인에 BNL을 택하면 정렬이 인덱스를 못 타고, 댓글수 DEPENDENT SUBQUERY가 정렬 전 전 행에서 실행된다. 실측: 전체 처리량 2.8 → 96.2 ops/s. 자바 코드 무변경 — 반환 컬럼·파라미터가 동일해 PostSummaryRow 매핑 그대로. 4개 분기(카테고리·커서 유무)와 인기 글 결과 id가 원본 쿼리와 완전 일치함을 실DB로 검증했다.

P1③ 관리자 검색 — LIKE '%키워드%'

개선 후 최대 병목(p50 2.7초). 앞 와일드카드 LIKE는 B-tree 인덱스를 탈 수 없다. 단기: 결과 상한 + 기간 기본 필터로 스캔 범위 축소. 중기: MariaDB 한국어 검색은 Mroonga 엔진, 규모가 커지면 검색 엔진 분리. 주문번호 검색은 현재 43ms지만 데이터에 선형 비례 — 주문번호는 후방 일치가 대부분이므로 접두 LIKE('ORD…%')로 유도하면 인덱스를 탄다.

P1④ 좋아요 토글 데드락 제거

SELECT EXISTS를 없애고 INSERT IGNORE의 영향 행 수로 분기하면 check-then-act 경쟁과 갭락 교차가 함께 사라진다: 영향 1행 → like_count +1, 0행 → DELETE 후 영향 1행이면 −1. MyBatis insert/delete는 영향 행 수를 반환하므로 CommunityService.toggleLike 몇 줄 수정으로 끝난다. 보조로 데드락(1213) 발생 시 1회 재시도를 감싸면 잔여 케이스도 흡수.

P2⑤ 통계 대시보드 날짜 인덱스 — 주문 도메인(주환)과 합의 필요

aggregateOrderStats의 서브쿼리 4개가 created_at·picked_up_at·canceled_at 풀스캔(부하 시 p50 994ms). orders(created_at) / (picked_up_at) / (canceled_at) 인덱스 추가 시 179ms → 20ms 실측(9배). orders는 주환 담당 테이블이라 V4에 포함하지 않았다 — 별도 V파일로 제안. 조회 빈도가 낮은 관리자 화면이므로 P2.

P2⑥ 조회수 핫로우 + 페이지 카운트 캐시

상세보기 트랜잭션 안의 view_count = view_count + 1은 인기글 행 잠금을 직렬화한다(이전 측정: 같은 행 집중 시 처리량 −39%). 메모리 카운터 + @Scheduled 배치 UPDATE(write-behind)로 분리 권장. 목록 진입마다 도는 COUNT(*)는 Caffeine 10~30초 TTL이면 충분.

5. 리팩토링 가능성 — 팀 규칙 준수 방식으로 적용 완료

①·②는 CLAUDE.md의 절대규칙을 지키는 형태로 feature/community-performance 브랜치에 커밋했다: 기존 V파일 무수정(새 V4 추가), community는 담당(현규) 도메인, 커밋 메시지 한글, dev 직접 push 없이 PR 대상. 단 global/config에 추가한 모니터링 설정은 규칙상 팀 합의가 필요하므로 PR에서 논의할 항목으로 표시했다.

결론: dev 코드베이스는 리팩토링 수용력이 매우 높다. Flyway·CI·스펙 훅이 있어 이런 성능 변경을 안전망 위에서 반복할 수 있고, 실제로 이번 개선의 핵심(34배)은 자바 코드 한 줄 수정 없이 SQL 파일 2개로 달성됐다.

측정 환경: 클라우드 샌드박스(공유 vCPU) · MariaDB 10.11 · InnoDB buffer pool 128MB(기본값) · 동시 16커넥션 × 15초 × (기준·개선) 2회. 절대 수치는 하드웨어에 따라 다르지만 단계 간 배율은 실행 계획 차이에서 오므로 재현된다. 스키마는 dev의 Flyway V1~V3 + R__dev_seed로 구축, 부하 데이터는 게시글 10만·댓글 30만·좋아요 10만·주문 10만·주문항목 10만·회원 202.
